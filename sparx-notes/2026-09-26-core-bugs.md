## Bug 1 — media delivery failure not fed back

**Production root cause (confirmed at `e0862e609ac`, the last main commit before the `2026.7.2`
version bump, standing in for `2026.7.1-2` since no release tag exists):**
`src/agents/tools/media-generate-background-shared.ts` `wakeMediaGenerationTaskCompletion` fell back
to `tryDeliverMediaGenerationDirect`, which sent directly to `requesterOrigin` and, on failure, only
logged a warning and returned `false`. The caller then logged `onWakeFailure("... not confirmed")`
and stopped — nothing was queued back to the session. This reproduces the reported journal sequence
"Delivery failed" → "wake failed" → "delivery was not confirmed" when the LINE outbound validator
(`extensions/line/src/outbound-media.ts` `resolveLineOutboundMedia`, intentionally correct — not
touched) rejects a non-HTTPS local media path.

**Current main:** `tryDeliverMediaGenerationDirect` no longer exists. Media completions unconditionally
route through `enqueueClaimedSessionDelivery` into a durable per-session delivery queue
(`subagent-announce-delivery.ts` `durableGeneratedMediaHandoff`), and a failed send (e.g. the same
LINE rejection) causes `src/gateway/server-restart-sentinel-agent-delivery.ts`
`evaluateQueuedGeneratedMediaAgentResult` to re-arm the requester's agent run with a "Generated media
still missing" prompt, up to `MAX_SESSION_DELIVERY_RETRIES = 5`
(`src/infra/session-delivery-queue-recovery.ts`), after which the task is marked terminal/`blocked`
and the generated-media references are retained on the task record (kept since 2026.9.2, PR #131921).

**Caveat:** upgrading fixes the *feedback* (the agent learns delivery failed and gets to retry/report
it), not the *delivery* — LINE still cannot carry a local file path, so a retry against the same
local media will keep failing until the media has a public HTTPS URL. That is a separate,
LINE/media-hosting-level follow-up, not part of this bug.

**Docs note:** `docs/automation/tasks.md`'s "Session-queued delivery … system event … next heartbeat"
text describes the *general* task-registry notifier
(`src/tasks/task-notification-routing.ts` `queueTaskSystemEvent`), which media tasks opt out of via
`notifyPolicy: "silent"`. It does not describe the actual media-completion delivery mechanism above.
Worth a docs follow-up, but not required to resolve the production symptom.

## Bug 2 — subagent result delivered to the wrong session

At the production-era commit `dbf837f574f` (standing in for `2026.7.1`, no release tag exists):
- Every session rollover minted a brand-new `sessionId` (`crypto.randomUUID()` in
  `src/auto-reply/reply/session.ts`).
- No mechanism stopped a parent's unfinished subagents before a reset/rollover.
- Completions had no `completionRequesterSessionId` and resolved their delivery target purely by
  session *key*, not a pinned session identity.

So while a parent session was parked in a `sessions_yield` wait, any rollover of that session key
(idle/daily rollover, `/new`, `/reset`) orphaned the old session id and the subagent's completion was
delivered to whatever new session id now occupied that key — matching the reported symptom.
`"Heartbeat check failed"` itself is, and was, only user-facing failure copy
(`src/agents/failover/user-copy.ts`) — it never mints a session on its own, in production or on
main; the actual replacement came from an ordinary rollover racing the yield.

Current `main` closes this gap in four separate, dated commits:

| Guard | Commit / PR | Date | First release |
|---|---|---|---|
| Implicit idle/daily rollover resets **in place**, keeping `sessionId` (only `lifecycleRevision` rotates) | `9ae9fcb1cdd` (#112988) | 2026-07-23 | 2026.8.1 |
| Explicit `/new`, `/reset`, and the gateway reset **stop the parent's unfinished subagents before committing** | `b28d51e01e7` (#140417) | 2026-09-06 | 2026.9.3 |
| Private (`completionTarget: "parent"`) completion pinned to the spawning `completionRequesterSessionId` | `7a168d3d4bd` (#147206), `523973ab6e7` (#148405) | 2026-09-14 | 2026.9.5 |
| Settle-wake delivers to the requester after it yields | `e2e5b0b7fe6` (#155348) | 2026-09-22 | 2026.9.6 |

Verified on current main (`8eed7e85638`) via:
```
node scripts/run-vitest.mjs run \
  src/auto-reply/reply/session.heartbeat-no-reset.test.ts \
  src/infra/heartbeat-runner.subagent-session-guard.test.ts \
  src/agents/subagents/registry/subagent-reset.lifecycle.test.ts \
  src/agents/subagents/registry/subagent-registry-requester-yield.test.ts
```
→ all 3 shards passed (52/52 tests in the captured shard). No code change was made; no new test was
needed since the guard is already present and covered.

**Recommendation:** upgrade — a cherry-pick onto `2026.7.1` is not practical, since these fixes build
on the SQLite session store and in-place-reset rework shipped between `2026.7` and `2026.9`. Production
needs **≥2026.9.3** for public-completion pinning and **≥2026.9.6** for the full post-yield delivery
guarantee.

**Known residual (current main, likely a separate design question, not this bug):** an *implicit*
idle/daily rollover of a still-yielding parent does not defer or cancel its children
(`deferImplicitRolloverForActiveRun` only covers active runs); the child's result then lands in the
same session id post-reset, which the parent's turn history no longer shows in context. Flagging for
awareness, not filing as part of this bug.

## Bug 3 — delivery mirror / direct session key missing

No reproducible defect found. Investigation (on current main, cross-checked against the
production-era source at `dba64d574f6^`) turned up three distinct, non-regressed conditions that
each independently produce "no mirror line anywhere" / "only a group key exists for this user":

- **(A) Default `dmScope`:** `buildAgentPeerSessionKey` (`src/routing/session-key.ts`) only creates a
  `:direct:<peer>` key when `dmScope` is `per-peer`/`per-channel-peer`/`per-account-channel-peer`.
  Under the documented default (`dmScope: "main"`, `src/infra/outbound/base-session-key.ts`), a
  user's 1:1 has no `:direct:` key at all, while any group they share still gets a `:group:` key —
  exactly "only a group key existed". `openclaw sessions cleanup --fix-dm-scope` also removes existing
  direct rows if `dmScope` is changed back to `main`, which would explain a key disappearing in early
  September without any code defect.
- **(B) Explicit `sessionKey` override on `send`:** `src/gateway/server-methods/send.ts` lets a caller
  override the route's derived session key (e.g. sending from a group session); the mirror and route
  then follow the caller's key, not a freshly derived `:direct:<user>` key. Pinned by
  `send.test.ts` "lowercases provided session keys for mirroring".
- **(C) Gateway-executed message-tool sends to a different conversation write no mirror anywhere:**
  the closest match to "no mirror line anywhere, while other sends mirrored fine". Telegram (and some
  WhatsApp/Discord actions) always execute `send` through the Gateway
  (`extensions/telegram/src/channel-actions.ts` `resolveExecutionMode`); the Gateway branch of
  `message-action-send.ts` commits the route and returns without building the core mirror, and
  `message.action` forces `suppressTranscriptMirror: true` for `send`
  (`src/gateway/server-methods/send.ts`). The only remaining mirror,
  `mirrorDeliveredSourceReplyToTranscript` (`src/infra/outbound/source-reply-mirror.ts`), only writes
  when the target matches the *current source conversation* — so a send from a group session to a
  different user's 1:1 mirrors nowhere. This is pinned by
  `send.test.ts` "does not mirror message.action sends to a different target" (added `0df9f297b60`,
  PR #84837, 2026-05-22) and reproduces identically on the production-era source
  (`message-action-runner.ts` `runGatewayPluginMessageActionOrNull`) — i.e. it predates production and
  is not a September regression.

Fixing (C) would mean widening transcript-mirror ownership beyond the current-source conversation,
which `src/infra/outbound/AGENTS.md` explicitly scopes ("does not widen transcript-mirror … ownership")
and which is a product/ownership decision, not a minimal bug fix — so no change was made.

**To actually pin the specific September incident**, we'd need from the production logs: the channel,
the session's `dmScope`/`groupScope`/`identityLinks`, which send path was used (agent message tool vs.
`openclaw message send` vs. cron/heartbeat, and whether `sessionKey` was passed explicitly), and the
session the agent was running in when it sent. A Telegram (or Gateway-mode WhatsApp/Discord)
message-tool send from a group session to a user's DM under default `dmScope: main` reproduces the
whole reported picture via (A) + (C) alone, with no code defect involved.
