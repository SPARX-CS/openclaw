# Carry set for 2026.9.6: runaway completion delivery (#20)

Branch `sparx/carry-2026.9.6`, based on upstream tag `v2026.9.6` (`eb377ac59e6`).
It consolidates fix PRs #2, #3, #4 and #6 into one carry set. The inputs were PR #5 (Opus analysis), PR #8 (Sonnet analysis) and PR #7 (upgrade notes).

Scope: OpenClaw core, and only the incident path. The requester reply had ended, completions found `no_active_run`, and each one fell back to a Gateway `agent` hand-off into agent-command. Context-delivery policy is unchanged.

## Result

- **Carry:** 3 fix commits plus 1 scenario test.
- **Kept:** #4, extended to cover subscription usage limits, and #2 with a trimmed test.
- **Dropped:** #3 and #6.
- **Capability:** the carry set removes nothing. `image_generate` and `sessions_spawn` stay available to workers, raw history is still passed and reseeded where 9.6 does so, and no config change is required.
- **Mitigations withdrawn for 2026.9.6:** these had been recommended in PR #5/#8 §C.
  - `tools.deny: ["sessions_spawn","image_generate"]` conflicts with X4.
  - `reseedFromRawTranscriptWhenUncompacted: false` conflicts with X2. It exists only in 7.1-2 and is retired in 9.6.
  - The scenario test below shows 9.6 plus this carry set passes the incident criteria without either one.

## 3. Scenario test

File: `src/agents/subagents/announce/completion-handoff-runaway.scenario.test.ts`. It runs one DM session (`agent:main:discord:direct:requester`, claude-cli) in incident order:

1. **User DM turn.** The turn runs through the real `agentCommandFromIngress` → prepare → model fallback → attempt-execution → `runCliAgent` → `prepareCliRunContext`. The session-stable reply mode comes from dispatch's real policy helpers. The main claude-cli binding and its `messageToolPolicyHash` are persisted in the real SQLite session store.
2. **8 `image_generate` completions arrive with no active run.** Each goes through the real `wakeTaskCompletion` → `deliverSubagentAnnouncement` → durable session-delivery queue → `drainPendingSessionDelivery` → internal Gateway agent-turn facade → agent command. Each completion produces exactly 1 turn and 1 CLI execution, resuming the main session id with `reuse` and the user-turn hash.
3. **Re-delivery of an already delivered completion id.** No new turn, and 8 channel sends in total.
4. **Worker completion hand-off held past `announceTimeoutMs` before admission.** It is cancelled with 0 CLI executions, so no orphaned turn delivers later.
5. **Retry of that worker completion.** Exactly 1 ok turn, resuming the main session. This is the direct subagent hand-off in a DM, with request mode `message_tool_only`.
6. **Hand-off whose fallback chain is exhausted on `billing` (opus → sonnet).** 1 turn, not 4. Both candidates resume the main session.
7. **Binding check.** The main claude-cli binding (sessionId and hash) is still in the store.

**Doubles (bypassed boundaries):**
- the claude-cli subprocess (`executePreparedCliRun`);
- the Anthropic plugin backend definition, replaced by a test backend with the same reuse-relevant fields;
- Gateway request auth, preflight and the admission/idempotency turn service, replaced by a minimal `startTurn`; the facade itself is real;
- the queued-media owner's param mapping;
- the channel send;
- config IO.

**Results on the carry branch:** 7/7 pass. Test time is about 13 s: 7 s is the first turn's cold imports, later turns take about 0.4–0.8 s. Shard wall time is 40–60 s with `--maxWorkers=1`.

**Mutation proof** (source restored afterwards). M2 and M3 reproduce 7.1-2 behavior:

| Mutation | Fails |
|---|---|
| M1: #4 reverted (`attempts.length > 0` counts as transient) | Stage 6: `['error','error','error','error']` instead of `['error']`, i.e. the hand-off was replayed 4× |
| M2 (7.1-2 hash split): agent-command uses the request's own reply mode for binding facts | Stage 5: hash `3ae4a980…` → `dd1ac522…`, `reuse.mode` `invalidate` (message-policy), no resume id, i.e. a fresh session and reseed. Stage 6: fresh session. Stage 7: the store binding is replaced by the fresh session |
| M3 (7.1-2 binding clear): clear on any `FailoverError` | Stage 6: the fallback candidate runs with `reuse.mode: none`. Stage 7: no claude-cli binding left |

Under M2, the image turns (stage 2) do not split, because 9.6 queued media turns request `automatic`. Only the direct subagent hand-off (`message_tool_only`) splits, which matches the 7.1-2 hash table in PR #5.

**Scenario gaps (not proven here):**
- "No reseed prompt" is proven only through reuse mode, resume id and hash. With the double, prepare never builds the OpenClaw history prompt, so a direct reseed-prompt assertion could not fail and was removed.
- Dedupe of a re-delivered *subagent* completion id relies on the Gateway turn-service idempotency, which is bypassed. Re-delivery is proven for image completion ids, where the real SQLite queue dedupes.
- The queue owner's retry policy after a billing failure *inside a queued media turn* is not exercised (R3).
- The #2 fresh-retry path is proven at the attempt-execution level, not in this scenario.
- Gateway admission is emulated. The cancel-on-deadline itself is real facade code.

## 6. Remaining risks

- **R1: quota message wording (UNVERIFIED).** The production journal text after "transient failure, retrying n/4:" is still unknown.
  - Some messages classify as unclassified, which counts as transient, so commit 3 does not cover them. An example is `You've hit your limit · resets 11pm`.
  - For those messages the inner loop still replays up to 4× per registry cycle.
  - Next step: grep the 2026-09-26 journal for that text. If it is unclassified, add the wording to the failover message patterns at their owner (`src/agents/failover/message-patterns.ts`).
- **R2: outer redelivery is still time-boxed, not count-boxed.** After a non-transient failure, 9.6 retries about 9 times over 30 min (15 s→5 min backoff), one turn each with this carry. That is by upstream design (durable delivery), and each attempt fails fast while quota is out. If a failed hand-off turn posts a user-visible error each time, the user can still see several error notices over 30 min. **UNVERIFIED:** the failure-copy delivery on hand-off turns was not traced.
- **R3: queued media-turn failures.** Image completions on 9.6 go through the durable session-delivery queue. That queue's retries after a billing failure (`failSessionDelivery`, about 6 attempts within the deadline) were not exercised by the scenario.
- **R4: D.2 is still open.** A completion turn that cannot resume (any future fingerprint split: cwd, mcp, auth, missing native transcript) still starts a fresh session with a raw-transcript reseed and then discards that session. Every later completion repeats this. The scenario shows it does not happen for message-policy on 9.6. Nothing prevents a future split, and the scenario test is the tripwire.
- **R5: the LINE WORKS plugin (UNVERIFIED).** If the plugin passes an explicit `replyOptions.sourceReplyDeliveryMode` on user turns, the user-turn hash can differ from the completion-turn hash (PR #5 A step 3). The scenario uses a generic DM channel. Before rollout, check `reuse=` on completion hand-offs in 9.6 staging logs; it should read `reuse` or `reuse-with-drift`, never `invalidated:*`.
- **R6: no per-session circuit breaker** for completion-driven turns (PR #5 D.4). This is an upstream feature question, not part of this carry.
- **R7: the claude-cli resume id (UNVERIFIED against the real binary).** The scenario assumes a resumed claude-cli run keeps its session id, so preserved turns keep a valid binding.
