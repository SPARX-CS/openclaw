# Upgrade notes: openclaw@2026.7.1-2 → 2026.9.6 — 2026-09-26

Scope: SPARX production upgrade planning from `openclaw@2026.7.1-2` (node 22) to `2026.9.6`
(requires node >=24.16.0 <25 || >=26.1.0, confirmed in `package.json` `engines` on the `v2026.9.6`
tag). Comparison is source-to-source: `git` tags `v2026.7.1-2` (commit `0790d9f593a`) and `v2026.9.6`
(commit `eb377ac59e6`) from `openclaw/openclaw`, fetched read-only into local worktrees — the SPARX
fork carries no release tags of its own. Bugs 1–3 reuse and cross-check the investigation already
committed by the sibling `openclaw-core-bugs` routine on `sparx/notes`
(`sparx-notes/2026-09-26-core-bugs.md`, commit `76f39c7272`); this file does not duplicate that
work's code changes (none were made there) and does not open competing fix branches for bugs 1–3.

## Task B — upgrade risk notes (2026.7.1-2 → 2026.9.6)

Sources: `CHANGELOG/2026.{7.1,8.1,8.2,9.1..9.6}.md` in the `v2026.9.6` worktree (`v2026.7.1-2` ships one
flat `CHANGELOG.md` — the per-release `CHANGELOG/` directory was introduced during this window) plus
direct `diff -rq`/`diff -u` between the two release worktrees.

### 1. claude-cli backend (`cliSessionBindings`, resume)

No changelog entry names `cliSessionBindings`/`image_generate`/"synthetic client" verbatim — treat
bug 4 above as a source-level finding, not something the changelog documents as fixed. Real, relevant
changes: `CHANGELOG/2026.9.1.md:52` — "stale CLI recovery cannot replace newer sessions" and "queued
cold turns keep CLI continuity" (CLI-session-binding/resume race fixes). New test coverage exists only
in `v2026.9.6`: `src/auto-reply/reply/agent-runner-execution-cli-sessions.test.ts` already covers
*adjacent* `image_generate`/`cliSessionBindings` scenarios (aborted/detached-turn preservation) but not
the successful-completion persistence gap bug 4 fixes. Separately, `src/gateway/session-create-service.ts`
(552→1606 lines) adds `authorizedPluginCreation`, a stricter gate that now hard-fails session creation
if `params.authorizedPluginId !== params.initialEntry.pluginOwnerId` when inheriting
`cliSessionBindings`/`providerOverride`/`modelOverride` onto a new session — new, not present in
2026.7.1-2.
**Check pre-upgrade:** none beyond the normal upgrade; no config key changed.
**Verify post-upgrade:** exercise an `image_generate` tool call in a `claude-cli` session and confirm
`cliSessionBindings["claude-cli"].sessionId` stays continuous across the media turn (this is exactly
what PR #3 above fixes — verify with that PR's regression test or manually).

### 2. Plugins/extensions loading (LINE WORKS custom plugin + bundled LINE extension)

**LINE WORKS** is not mentioned anywhere upstream (SPARX's own plugin) — compatibility is purely an
SDK-contract question. **Bundled `extensions/line/`**: `compat.pluginApi`/`peerDependencies.openclaw`
bumped `>=2026.7.1` → `>=2026.9.6`; the old top-level `channelEnvVars` manifest field was removed,
replaced by `channel.configuredState.env.allOf` + a full `channel.setup.fields[]` block and
`setupFeatures.configPromotion: true`; new `doctorContract.stateMigrations` (a LINE-specific state
migration Doctor now owns); dependency bumps `@line/bot-sdk` 11.1.0→11.2.0, `zod` 4.4.3→4.6.5, added
`typebox`. General plugin loader/SDK churn is broad (700+ files) but expected per the "small core,
capable plugins" model; new `src/plugins/plugin-version-drift.ts` means Doctor can now flag a plugin
whose manifest still declares `compat.pluginApi: ">=2026.7.1"` (or omits it) as version-drifted after
the upgrade even if it still loads.
**Check pre-upgrade:** confirm LINE WORKS's manifest declares a `compat.pluginApi`/`peerDependencies.openclaw`
range satisfied by 2026.9.6; run `openclaw doctor` for a version-drift warning; if it relies on the old
top-level `channelEnvVars` field, confirm compatibility (bundled LINE moved off it).
**Verify post-upgrade:** `openclaw plugins list`/`openclaw doctor` shows LINE WORKS healthy with no
version-drift warning; bundled LINE still authenticates with the existing `LINE_CHANNEL_ACCESS_TOKEN`/
`LINE_CHANNEL_SECRET` env vars.

### 3. Config schema/validation

**`memorySearch` provider `gemini`**: unchanged — already present in 2026.7.1-2, not newly added; only
a cosmetic help-text wording change. **`imageGenerationModel`**: key unchanged in both trees, no
renaming/removal. **`contextInjection`/bootstrap files (AGENTS.md/MEMORY.md)**: char limits are
**unchanged**: `DEFAULT_BOOTSTRAP_MAX_CHARS = 20,000` per file, `DEFAULT_BOOTSTRAP_TOTAL_MAX_CHARS =
60,000` total, in `src/agents/embedded-agent-helpers/bootstrap.ts` in both trees, confirmed by
`commands-context-report.test.ts` and `docs/automation/hooks/bundled-hooks.md:73`. **The "120,000"
figure in the task prompt could not be verified** — every `120000`/`120_000` hit in source is a
millisecond timeout, not a character limit; **mark it unverified**, likely a misremembering. The
`DEFAULT_BOOTSTRAP_MAX_CHARS`/`_TOTAL_MAX_CHARS` constants also moved from exported to module-private
(behind `resolveBootstrapCharLimit()`) — implementation detail only, not config-facing.
**Check pre-upgrade:** nothing required for these three keys; no schema break.
**Verify post-upgrade:** `openclaw config get memorySearch.provider`/`.fallbackProvider` still accept
`gemini`; context-report output still shows "Bootstrap max/total: 60,000 chars" unless overridden.

### 4. Sessions store (`sessions.json`, delivery-mirror, `sessions_yield`/`sessions_spawn`)

**Major change**: the session store moved from the JSON `sessions.json` file model toward per-agent
**SQLite** databases during this exact window (previewed in `CHANGELOG/2026.7.1.md:2396`, already in
2026.7.1-2, as "migration guidance ahead of the planned SQLite transition"; `CHANGELOG/2026.8.1.md:81`
adds `openclaw backup sqlite`). New migration machinery: `src/infra/state-migrations.session-store.ts`,
`state-migrations.legacy-sessions.ts` (reads legacy `sessions.json`, writes SQLite),
`doctor-session-sqlite-recovery-inventory.ts`. Migration is automatic on first startup/Doctor run after
upgrade — no hand-migration needed, but back up `sessions.json` and the agent state directory first per
the "back up before mutating" update contract. `delivery-mirror` mechanism is still present, refactored
into `src/infra/outbound/` (new file names vs OLD's `session-utils.fs.ts`); no evidence of a
plugin/public-facing API break, but **unverified** whether any external tooling reading the old file
layout directly would break. `sessions_spawn`/`sessions_yield`: `CHANGELOG/2026.9.1.md:52-53` —
"yielded CLI spawns settle" and `sessions_spawn` "declares its completion-message expectation" (both
behavioral fixes, not schema breaks).
**Check pre-upgrade:** back up `sessions.json`/agent state dirs; ensure disk headroom for SQLite WAL
files alongside old JSON during migration; don't run two Gateways against the same state dir mid-upgrade.
**Verify post-upgrade:** `openclaw doctor` shows no session-store migration warnings/failures;
`openclaw sessions tail`/`sessions list` work; old `sessions.json` is retained (not deleted), so
rollback stays possible.

### 5. Heartbeat

Interval/timeout defaults **unchanged** (`DEFAULT_HEARTBEAT_EVERY = "30m"`,
`DEFAULT_HEARTBEAT_ACK_MAX_CHARS = 300`, `DEFAULT_HEARTBEAT_TIMEOUT_SECONDS = 600`). **One default
changed**: `DEFAULT_HEARTBEAT_TARGET` went from `"none"` (2026.7.1-2) to `"owner"` (2026.9.6) — a
heartbeat's default delivery target is now the workspace owner instead of nothing. The
"Heartbeat check failed" recovery copy is preserved verbatim (moved modules, additive
`renderHeartbeatRunFailureCopy(reason?)`). `CHANGELOG/2026.9.1.md:50` — watchdog timeout honored,
immediate main-session wakes admitted with heartbeat disabled, first-alert preamble fixed — bug fixes,
no config-key change.
**Check pre-upgrade:** if SPARX relies on heartbeat having no default delivery target, set
`agents.defaults.heartbeat.target` explicitly rather than depending on the old implicit default.
**Verify post-upgrade:** force a heartbeat failure and confirm the recovery message/delivery target
match expectations; `openclaw heartbeat status` now shows Gateway ages (2026.9.1).

### 6. Node version requirements

`package.json` `engines.node`: 2026.7.1-2 = `>=22.22.3 <23 || >=24.15.0 <25 || >=25.9.0`; 2026.9.6 =
`>=24.16.0 <25 || >=26.1.0`. **Node 22 and Node 25 support are both dropped**; the Node 24 floor rises
24.15.0→24.16.0. `CHANGELOG/2026.9.3.md:16` ("Breaking — Node runtime"): requires Node ≥24.16.0 (24.x)
or ≥26.1.0 (26 recommended); explicitly tied to a Node-internal **SQLite text-truncation** bug that
this release's new SQLite-backed session store (item 4 above) depends on — the changelog explicitly
says to upgrade Node *before* upgrading OpenClaw. `packageManager` also bumps `pnpm@11.2.2` →
`pnpm@12.4.0`. This container's own toolchain needed the same jump — the pre-existing dev environment
here runs Node 22.22.2, and `pnpm install`/`pnpm build` refuse to run against it (`this OpenClaw release
requires Node >=24.16.0 <25 || >=26.1.0`) until Node was upgraded via `nvm install 24.21.0`, confirming
the constraint is enforced at install time, not just declared.
**Check pre-upgrade:** upgrade the production host's Node to ≥24.16.0 (or ≥26.1.0) **before** running
`openclaw update`; confirm no native modules pinned to the Node 22 ABI; confirm pnpm ≥12 is available
for source builds.
**Verify post-upgrade:** `node -v` reports ≥24.16.0/≥26.1.0; `openclaw doctor` reports no unsupported-runtime
warning; no SQLite text-truncation errors in Gateway logs during/after the sessions.json→SQLite migration.
